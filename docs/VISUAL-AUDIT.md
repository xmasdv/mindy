# Mindy Visual Surface Audit

This audit defines the user-facing surface baseline for reconstructing Mindy as a visually independent Thunderbird 140.13 downstream. It identifies 80 surface families, records where inherited behavior currently enters the UI, and assigns an isolation and verification expectation to each family.

## Decision Summary

| Item | Audit result |

| Family counts | SH 7, AC 8, MW 10, RD 6, CP 7, SR 4, CA 7, CT 5, ST 9, SY 11, SF 3, AX 3 |

## Method

The audit triangulated four evidence classes:

1. Visual authority in [`../DESIGN.md`](../DESIGN.md), the approved [navy/teal inbox mockup](../assets/design-concepts/mindy-inbox-mockup-v2-navy-teal.png), and the production [Mindy mark](../assets/brand-production/mindy-mark.svg).
2. The rejected partial implementation in patches `0002` and `0007`-`0013`. These patches are evidence of coupling, token fragmentation, and limited coverage; they are not visual authority.
3. The applied Thunderbird 140.13 source under `C:\mozilla-source\mindy\vendor\gecko`, checked at representative shell, account, mail, compose, calendar, address-book, preferences, and secondary-product paths.
4. Runtime evidence under `C:\Users\chris\AppData\Local\Temp\opencode\mindy-visual-20260728-172836\evidence`, including first-run, account-free shell, inherited privacy content, About, narrow/focus, restored-wide, process cleanup, and observed provider requests.

CodeGraph was used first for repository ownership and blast-radius checks. The external Gecko checkout had no CodeGraph index; creating one would have changed prohibited external state, so external verification was limited to targeted path and symbol reads after that failed attempt.

### Counting Convention

A surface family is counted when it has a distinct user job, entry route, state model, native or web boundary, or verification strategy. Variants that share all of those are states of one family, not additional families. Native, provider-hosted, and operating-system surfaces remain in the inventory as inherited or wrapped boundaries because users still experience them as part of Mindy.

### Boundaries

- This is a visual ownership audit, not a request to replace Thunderbird protocol, storage, security, accessibility, or command behavior.
- Patches are implementation evidence only. The approved mockup and design system govern visual direction.
- Provider-hosted OAuth, privacy, support, and add-on content cannot always be restyled. Mindy must own the transition, context, consent, and return state around them.
- Operating-system dialogs and notifications remain native where native behavior is required; Mindy owns invocation context, labels where APIs permit them, and visual continuity before and after the boundary.
- Local AI is explicitly deferred and out of scope. No other user-facing family is omitted.

## Severity Findings

| Severity | Finding | Evidence | Required response |
|---|---|---|---|
| P1 | Visual reconstruction was reduced to recoloring. | Runtime retained Thunderbird composition, hierarchy, and broad inherited styling despite navy/teal accents. | Rebuild surface composition through Mindy components while preserving controllers. |
| P1 | Source, patch, and runtime can drift independently. | Ordered patches, applied Gecko files, and the built executable represent separate states. | Record source pins, patch applicability, artifact identity, and screenshot provenance in every validation run. |
| P1 | Current patches couple directly to high-churn upstream markup. | Root data attributes, stylesheet links, and selectors target `messenger.xhtml`, `about3Pane.xhtml`, `aboutMessage.xhtml`, account setup, compose, and account central. | Restrict upstream edits to reviewed hooks and route presentation through stable adapters. |
| P1 | Tokens and component rules are fragmented. | `mindyMail.css`, `mindyWorkspace.css`, `mindyMailWorkspace.css`, `mindyMessageReader.css`, `mindyCompose.css`, and `mindyFirstRun.css` redefine overlapping roles. | Establish one semantic token package and one primitive layer before surfaces migrate. |
| P1 | Most inherited products are visually unowned. | Calendar, contacts, settings, security, extension, native, chat, feeds, and newsgroup families had no Mindy reconstruction. | Keep all 80 IDs in the implementation and screenshot matrices. |
| P1 | Upstream updates can silently alter appearance. | Inherited markup and styles continue to render whenever a Mindy selector does not cover them. | Fail closed on contract drift, patch conflict, missing screenshots, and unresolved visual deltas. |
| P2 | Accessibility evidence is incomplete. | Focus was captured, but keyboard paths, zoom, screen-reader semantics, high contrast, reduced motion, and reflow were not systematically verified. | Add per-surface accessibility states and AX compatibility gates. |
| P2 | Responsive behavior is incidental. | Narrow runtime showed inherited collapse behavior rather than an explicit task topology. | Define wide, medium, narrow, zoom, and pane-restoration contracts. |
| P2 | Provider branding leaks into Mindy. | Runtime title exposed a Thunderbird privacy notice and Mozilla-hosted content. | Wrap provider transitions and label inherited content honestly; never imply visual ownership of remote pages. |
| P2 | Account-free paths dominate first-run evidence. | Compose was blocked without an identity; populated mail states were not captured. | Use synthetic, offline-safe fixtures and provider-dependent manual validation without real credentials. |
| P2 | Native lifecycle identity is uneven. | About was branded, while crash, update, install, print, picker, and OS integration families remain separate boundaries. | Define inherited/native ownership and platform screenshot/manual gates. |
| P2 | Performance risk is distributed across CSS and document loading. | Multiple surface stylesheets and deep selectors increase invalidation and startup work. | Budget stylesheet count, selector scope, layout shifts, and startup regressions. |
| P2 | Theme behavior is not semantic. | Current patches hard-code surface-specific light colors and sparse dark-mode exceptions. | Resolve light, dark, system, and high-contrast values from semantic roles. |
| P2 | Visual verification is too narrow. | Existing browser contracts mainly prove hooks and selected computed values. | Pair static contracts with runtime screenshots, interaction state capture, and fresh independent review. |

## Positive Findings

- The approved mockup establishes a coherent Precision Workspace direction: deep structural navy, restrained teal interaction, compact scanning regions, and spacious reading.
- The production SVG mark provides an owned identity asset independent of Mozilla artwork.
- Existing patches demonstrate that scoped chrome stylesheets, root hooks, packaging entries, and focused browser tests are feasible.
- Thunderbird already supplies mature controllers, keyboard commands, protocol handling, localization infrastructure, and accessibility semantics that should be preserved behind adapters.
- Runtime evidence proves branded executable and About identity, stable account-free operation, responsive window capture, and clean process teardown.

## Audit Interpretation

The inventory is a reconstruction boundary, not a demand to replace 80 controllers. Thunderbird remains responsible for mature behavior. Mindy becomes responsible for the visual contract at every listed boundary through stable adapters, shared components, semantic tokens, and explicit treatment of native and provider-owned UI.

Implementation sequencing and work-unit acceptance are defined in [`VISUAL-RECONSTRUCTION-PLAN.md`](VISUAL-RECONSTRUCTION-PLAN.md). Package and update safety rules are defined in [`VISUAL-OWNERSHIP.md`](VISUAL-OWNERSHIP.md).
